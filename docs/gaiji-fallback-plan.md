# 外字フォールバック機能 計画書

対象端末に該当グリフが無く「?」や豆腐になる問題への対策。
2026-08-26 スパイク実施、設計着手。

## 背景 — 発端の要望

X (Twitter) 上の報告（2026-08-23）:

> Xteink X3で「𢌞り」これとか表示できないから「?」とかになるよりは
> 「[「廴＋囘」、第4水準2-12-11]り」とかの**表示のまま出力したい**んだけど…

> JIS第4水準フォント探して入れてみたけど結局Xteink X3上では「?」のまま

重要なのは、この要望が**「別の字に置換してほしい」ではなく「変換しないでほしい」**であること。
`𢌞` (U+2231E) には対応する第1・2水準の字が存在しないため、置換テーブルでは救えない。

### 現状の挙動

`chuki_utf.txt:1541` に以下のエントリがあるため、変換は**成功してしまう**。

```
U+2231E		𢌞	※［＃「廴＋囘」、第4水準2-12-11］
```

AozoraEpub3 からは端末にグリフがあるか見えないので、親切のつもりで `𢌞` を出力し、
端末側で豆腐になる。

### 欲しい出力形式は既にコード内にある

`AozoraEpub3Converter.java:1441-1443`（変換失敗時のフォールバック）:

```java
if (logged) LogAppender.info(lineNum, "外字未変換", chuki);
gaiji = "〓［＃行右小書き］（"+chukiValues[0]+"）［＃行右小書き終わり］";
```

`chuki_tag.txt:250-251` で `〓<span class="sup">（廴＋囘）</span>` になる。
要望どおりの出力だが、**変換に失敗したときしか発火しない**のが問題。

## スパイク結果

計測スクリプトは `AozoraGaijiConverter.loadChukiFile()`
(`src/com/github/hmdev/converter/AozoraGaijiConverter.java:54-90`) のパース処理を
忠実に移植して実行。有効エントリ数は `chuki_utf.txt` 7,949 件 / `chuki_ivs.txt` 522 件。

### 発見1: JIS X 0208 を境界にする案は破綻している

`chuki_utf.txt` の水準分布:

| 水準 | 件数 | 割合 |
|---|---:|---:|
| 第1・2水準 (JIS X 0208) | 63 | 0.8% |
| 第3水準 (JIS X 0213 面1) | 1,701 | 21.4% |
| 第4水準 (JIS X 0213 面2) | 2,434 | 30.6% |
| JIS外 (Unicode 拡張漢字等) | 3,751 | 47.2% |
| うち SIP (U+20000 以降) | 438 | 5.5% |

（数値は JDK 21 の `x-SJIS_0213` による実測。検証方法は「発見5」を参照。
Python `shift_jis_2004` での集計とは 2 件差があるが、コーデックのレパートリ差の範囲）

外字表とは定義上「標準外の字の表」なので、第1・2水準は 0.8% しかない。
**「第1・2水準までに留める」を選ぶと 99.2% が 〓 になる。**
`俠` `俱` `亍` のような第3水準の見慣れた字まで巻き添えになるため、この境界は採用不可。

### 発見2: 境界候補ごとの影響範囲

| 候補 | 抑止される件数 | 報告事例 `𢌞` を救えるか |
|---|---:|---|
| A: 第1・2水準まで | 7,886 (99.2%) | ○ だが巻き添えが甚大 |
| **B: 第3水準まで（第4水準と JIS外を抑止）** | 6,185 (77.8%) | **○** |
| C: JIS X 0213 まで（JIS外のみ抑止） | 3,751 (47.2%) | × |
| D: SIP のみ抑止（旧 `Gaiji32` 相当） | 438 (5.5%) | ○ |

`𢌞` は第4水準 (2-12-11) かつ SIP なので B と D の両方で救われる。
ただし第4水準 2,434 件のうち SIP は 438 件のみで、大半は BMP 内にあるため、
**D では第4水準の約 2,000 件が漏れる**。

注目すべきは **JIS外が 47.2%（3,751 件）と最大勢力**であること。
JIS の裏付けが全く無い純 Unicode 漢字なので、端末フォントに無い可能性が最も高い。
候補 C は「JIS 規格に無い字だけを注記表示にする」という穏当な線で、
報告事例は救えないが選択肢として提供する価値がある。

### 発見3: 実装地点が休眠状態で既に存在する

過去に同種の機能が作られ、コメントアウトされたまま残っている。

| 箇所 | 内容 |
|---|---|
| `AozoraEpub3Converter.java:2677, 2717, 2753` | `/*if (!gaiji32) { buf.append("〓"); ... }*/` 抑止本体 |
| `AozoraEpub3Applet.java:1836-1847` | UI（`jCheckGaiji32`、「4バイト文字」枠） |
| `AozoraEpub3Applet.java:221, 5225, 5448` | フィールド宣言・ini 読み書き |
| `AozoraEpub3.java:206, 289` | ini 読み込みと CLI オプション `-g4` |
| `AozoraEpub3Converter.java:2648, 2767` | `//TODO 非対応文字チェック`（4バイト文字側と U+FFFF 以下側の 2 箇所） |

ツールチップは「u+20000以降の4バイト拡張漢字をそのまま出力します。Kobo等で表示できない場合はチェックを外します」
＝候補 D 相当。

#### 休眠した原因（調査済み・重要）

**この休眠コードは「グリフ欠落」対策ではなく「Kobo の描画バグ」対策だった。**
削除したコミット `b35c55f`（2015-02-08、hmdev）の `README_Changes.txt` に理由が明記されている。

```
- 4バイト文字の出力設定を削除(Koboで4バイト文字以降が表示されない問題が解消したため)
```

「4バイト文字**以降**が表示されない」＝ 該当文字が豆腐になるのではなく、
**それ以降の本文が丸ごと描画されない**という重度の描画崩れ。
Kobo のファーム修正でこの問題が解消したため、機能ごと削除された。

同コミットで `setGaiji32(boolean)` が `setCharOutput(dakutenType, printIvsBMP, printIvsSSP)` に
置き換わり `gaiji32` フィールドが消えたため、参照していた 3 箇所はコンパイルを通すために
コメントアウトされた。UI と CLI `-g4` も同時に封じられている。
なお同コミットは代替として **1文字フォント埋め込み(`utf32FontMap` / `gaiji/*.ttf`)** と
**IVS 出力制御** を導入している。「捨てて、より良い手段に置き換えた」という流れ。

**したがって、この休眠コードを literal に復活させるのは誤り。**

| | 旧 `gaiji32` | 本機能 |
|---|---|---|
| 目的 | Kobo の描画バグ回避（解消済み） | 端末フォントにグリフが無い問題 |
| 判定 | 4バイト(SIP)かどうかの一律判定 | JIS 水準の閾値判定 |
| 出力 | 常に `〓`（情報ゼロ） | `〓（「廴＋囘」）` 注記付き |

挿入位置（`:2648` と `:2767` 付近）だけを流用し、判定と出力は `JisLevelUtil` ベースで新規に書く。
**1文字フォントの探索(`utf32FontMap`)より後ろに置くこと** — フォントが同梱されていれば
そちらで正しく表示できるので、抑止してはいけない。

### 発見4: 置換テーブル（機能2）は機能1の代替にならない

第1弾スパイクで、第1・2水準に自動で落とせる経路を計測:

| 経路 | 件数 | 備考 |
|---|---:|---|
| A: IVS 剥がし（`chuki_ivs.txt` の異体字セレクタ除去） | 490 / 522 | **自動生成可能・手作業ゼロ** |
| B: NFC 正規化（CJK 互換漢字 `塚` U+FA10 → U+585A 等） | 64 | テーブル不要・数行 |
| C: NFKC 正規化 | 233 | `㋐→ア` `‼→!!` など**副作用大。不採用推奨** |

**自動で救えるのは約 780 件、残り 7,562 件は落とし先が無い。**

## 設計方針

### 優先度（スパイクを受けて改訂）

1. **機能1: 外字変換の上限水準スイッチ** — 本体。要望に直接答える
2. **機能2: 内蔵置換テーブル（経路 A + B のみ）** — 補完。約 780 件
3. 第3・4水準フォント同梱 — 別途検討

### 機能1 の実装ポイント

判定を入れる場所が 2 系統ある。**両方必要**。

**(a) 注記経由（本命）— `convertGaijiChuki` (`AozoraEpub3Converter.java:1380-1450`)**

注記情報 (`chukiValues`) を保持しているのはここだけ。
変換結果 `gaiji` が確定した直後・`if (gaiji != null)` の成功分岐に入る前に水準判定を挟み、
閾値を超えていたら `gaiji = null` 相当にして**既存のフォールバック分岐 (`:1436-1447`) に合流させる**。
新しい出力経路を作らずに済む。

要望では水準コード（`第4水準2-12-11`）も残したいとあるが、
既存フォールバックは `〓（廴＋囘）` で `chukiValues[0]` しか使っていない。
`chukiValues[1]` に水準コードが入っているので、含めるかは設定で選ばせるか要検討。

**(b) 生の文字（補助）— `convertChar` 周辺 (`:2677, 2717, 2753`)**

テキストに注記を介さず `𢌞` が直接書かれている場合。
注記情報が無いので `〓` のみ。休眠コードの復活で対応。

**水準判定の実装（検証済み）**

`chuki_utf.txt` の「第4水準2-12-11」という水準情報は、
`AozoraGaijiConverter.loadChukiFile` が `chukiEnd = chukiCode+1` で `、` の手前を切り捨てるため
マップに残っていない。**注記由来でも `※［＃U+2231E］` の直接指定でも一律に効く**ため、
コードポイント判定を採用する。

JDK 21 の実測では **`x-euc-jis-2004` は存在せず**、SS3(0x8F) 方式は使えない。
一方 `x-SJIS_0213` は存在し、Shift_JIS-2004 の面付け規則
（面1 = lead 0x81-0x9F/0xE0-0xEF、面2 = lead 0xF0-0xFC）で水準を判別できる。

```java
static final CharsetEncoder SJIS  = Charset.forName("Shift_JIS").newEncoder();
static final Charset        S0213 = Charset.forName("x-SJIS_0213");

/** 0=第1・2水準 3=第3水準 4=第4水準 9=JIS外 */
static int level(String s) {
    if (s.isEmpty()) return 9;
    if (SJIS.canEncode(s)) return 0;
    if (!S0213.newEncoder().canEncode(s)) return 9;
    int lead = s.getBytes(S0213)[0] & 0xFF;
    return (lead >= 0xF0 && lead <= 0xFC) ? 4 : 3;
}
```

> `CharsetEncoder` はスレッドセーフでないため、実装時はインスタンス共有に注意。
> 上記は検証用スニペットであり、そのまま static 共有しないこと。

### 発見5: 判定規則の妥当性検証

`chuki_utf.txt` は注記テキスト自体に「第3水準1-14-2」「第4水準2-12-11」という
水準表記を持つ。これを正解データとして上記規則を全件照合した。

| 項目 | 件数 |
|---|---:|
| 水準表記があるエントリ | 3,698 |
| 規則と表記が一致 | 3,687 (99.70%) |
| 不一致 | 11 (0.30%) |

不一致 11 件は精査の結果、いずれも**規則の誤りではない**:

- `猪` `祥` `諸` `都` の 4 件 — 注記は「第3水準」だが、表が保持する字は包摂適用後の
  第1・2水準の字。判定 (=第1・2水準) の方が実態に即している
- 残り 7 件 — `※［＃「馬＋「柳の本字、第4水準2-14-72」のつくり」］` のように
  **注記の説明文の中に登場する別の字**の水準表記を、照合スクリプトの正規表現が拾ったもの

したがって判定規則は実用上 100% 正しいとみなせる。

**なお第1弾スパイクの数値は誤りだったため破棄した。**
Python の `euc_jis_2004` が JIS X 0213 面2 に加えて **JIS X 0212 補助漢字**まで
受理する（3,146 件）ため、補助漢字を第4水準として過大計上していた。
本書の数値はすべて `x-SJIS_0213` / `shift_jis_2004` ベースの確定値。

### 機能2 の実装ポイント

- 経路 A: `chuki_ivs.txt` から**ビルド時に**置換表を生成し `replace_jis.txt` として同梱
- 経路 B: NFC 正規化をコード内で実施（テーブル不要）
- 経路 C: **不採用**
- 適用は既存の `replaceMap` / `replace2Map` 経路（`AozoraEpub3Converter.java:422` 読み込み、`:3098` 適用）に乗せる
- ユーザーの `replace.txt` が内蔵より優先

### 設定の置き場所

- **ini にはフラグのみ**（例: `GaijiLevel=0|3|4|9`）。置換ペアを ini に入れない
- 理由: GUI 終了時に `AozoraEpub3.ini` が書き戻される既知の挙動があり、
  ini を肥大化させると配布物汚染事故（v1.6.0 リリース時に実際に発生）と混ざる
- 置換表本体は `replace_jis.txt` として同梱 + JAR 内リソース fallback
  （`chuki_*.txt` と同じ扱い。`AozoraEpub3Converter.java:322-334` に前例あり）

### UI

「文字」タブ（`AozoraEpub3Applet.java:2296` の `ui.tab.char`）に配置。

```
外字の変換:  ○ すべて変換（既定・現状維持）
             ○ 第3水準まで（第4水準以上は 〓（廴＋囘） 表示）
             ○ 4バイト文字のみ抑止
             ○ 変換しない
```

- **既定は現状維持**。端末によっては第4水準も表示できるため、勝手に見た目を変えない
- `presets/*.ini` は端末ごとにあるので、既定値をプリセット側で変える余地を残す
- **CLI にも同時配線する**こと。GUI のみだと narou.rb 経由（CLI を叩く）のユーザーに届かない。
  休眠している `-g4`（`AozoraEpub3.java:289`）を拡張する形になる
- i18n: `docs/narou-setup.md` と `docs/en/narou-setup.md` はペアで更新

### ログ

無言で本文表現を変えないこと。変換後に件数を出す。


### 発見6: 注記の面区点コードは注記名称より優先される（実装時に判明）

`convertGaijiChuki` の変換順序は以下で、**コード指定が注記名称より先**に試される。

```java
if (gaiji == null && chukiValues.length > 1) gaiji = codeToCharString(chukiValues[1]);  //面区点コード
if (gaiji == null) gaiji = toUtf(chukiValues[0]);                                        //注記名称
```

このため `chuki_utf.txt` のフィールド2 と実際の変換結果が食い違う行がある。

| 対象 | 値 |
|---|---|
| 注記 | `※［＃「けものへん＋睹のつくり」、第3水準1-87-79］`（`chuki_utf.txt:3277`） |
| フィールド2 | `U+732A`（JIS X 0208 の 猪 = 第1・2水準） |
| **実際の変換結果** | **`U+FA16`**（面区点 1-87-79 が指す互換漢字の 猪 = 第3水準） |

**水準判定は実際の変換結果に対して効かせる必要がある**（実装はそうなっている）。

本書の水準分布はフィールド2 を数えているため、この食い違いのぶんだけ誤差がある。
該当は発見5 の照合で見つかった包摂適用の 4 件程度（3,698 件中）なので、
分布の傾向と選んだ閾値には影響しない。回帰検知として
`GaijiFallbackTest.面区点コードが注記名称より優先される` で固定した。

なお `U+FA16` は NFC 正規化で `U+732A` に戻る。機能2 の経路B（NFC）がそのまま効く例。

## 決定事項（2026-08-26）

| 論点 | 決定 | 理由 |
|---|---|---|
| 既定値 | **現状維持（すべて変換）** | 既存ユーザーの出力を一切変えない。困っている人だけが設定を変える |
| UI 粒度 | **チェックボックス1個 +「詳細...」** | 「水準」を理解していなくても使える。細かい指定は奥に隠す |
| 表示形式 | **設定で選べる** | 報告者は水準コードまで残したい書き方。既定は簡潔な `〓（廴＋囘）` |
| PR 分割 | **機能1 と機能2 は別 PR** | 機能1 が本体。機能2 の 780 件は後追いでよい |

### レビューで見つかった実装バグ（2026-08-26・修正済）

**1文字フォントの免除が、注記経由の外字で効いていなかった。**

`convertGaijiChuki`（注記 → 文字）は `convertChar`（1文字フォント探索）より**手前**で動く。
生の文字側だけフォント探索の後ろに判定を置き、注記側では置いていなかったため、
`gaiji/u2231e.ttf` を配置しても `※［＃「廴＋囘」…］` は `〓` になっていた。
本書「休眠した原因」の節で「1文字フォントの探索より後ろに置くこと」と決めた方針に反していた。

修正: `isGaijiFallback` に `hasGaijiFont` の判定を追加し、
フォントが登録されている文字は水準に関わらず抑止しないようにした。
IVS 付き（`ivs16FontMap` / `ivs32FontMap`）と非 IVS（`utf16FontMap` / `utf32FontMap`）の
両方の命名に対応する。回帰テストは `GaijiFallbackTest` の
`一文字フォントがある文字は抑止しない` / `一文字フォントが無ければ抑止する`。

### Codex レビューの指摘（2026-08-26・修正済）

いずれも P2。「水準判定より手前で文字を出力してしまう経路が残っていた」という同じ形の漏れ。

**1. IVS 付きの文字が判定を素通りする**

`convertTcyText` の異体字セレクタ分岐は 4 つ（4バイト＋IVS(U+E0100〜) / 4バイト＋VS(U+FE00〜) /
2バイト＋IVS / 2バイト＋VS）あり、どれもフォント探索に失敗すると
その場で「基底字＋セレクタ」または「基底字のみ」を出力して `continue` していた。
水準判定はその後ろ（セレクタ無しの経路）にしか無かったため、
`𢌞` 単体は `〓` になるのに `𢌞` ＋ U+E0100 は素通りするという不整合が起きていた。
`JisLevelUtil` はセレクタを判定から除外する（含めると基底字の水準が常に `LEVEL_OUT` に潰れる）ので、
基底字は判定対象として正しく認識されている。

修正: 4 分岐すべてで、フォント探索の後・IVS 出力の前に判定を挟み、
置き換えるときはセレクタも一緒に読み飛ばす（単独のセレクタが本文に残らないようにする）。

**2. 同じ長さのルビが判定を素通りする**

`convertRubyText` は「本文とルビの長さが同じで、ルビが同一文字の繰り返し」のとき
1 文字ずつルビを振る専用の分岐に入り、`convertTcyText` ではなく
`convertReplacedChar` を直接呼ぶ。この経路には水準判定もフォント探索も無いため、
`俠《き》` は第3水準以上の設定でも `俠` のまま出力されていた。

修正: `convertReplacedChar` の先頭に判定を置き、`convertTcyText` を通らない直接出力経路の受け皿にした。
フォント探索が無い経路なので、判定は `isDirectCharFallback`（水準＋1文字フォントの有無）を使う。
4バイト文字は `char` 単位のこの関数ではペアを判定できないため、サロゲートは対象外にして
`convertTcyText` 側に任せる。異体字セレクタ自体も字ではないので置き換えない。

回帰テストは `GaijiFallbackTest` に 7 件追加（IVS/VS 付き 4 件、同じ長さのルビ 3 件）。

**副産物として見つけた既存バグ**（本 PR の scope 外・`docs/code-audit-followups.md` の「### 33.」に起票）:
同じ長さのルビの分岐は `char` 単位でループするため、本文が 4バイト文字だと
サロゲートペアが 2 つの `<ruby>` に分断され、単独サロゲートが XHTML に残る。
フォールバック機能とは独立に既定設定でも再現する。

### リリース前 dogfood で見つけたバグ（2026-08-26・修正済）

**仮名＋濁点/半濁点が、同梱の濁点フォントを使えるのに `〓` に置き換わっていた。**

v1.6.1 のリリース作業で配布物を作り、`test_data/test_gaiji.txt` を変換して見つけた。
同梱 `AozoraEpub3.ini` は `DakutenType=2`（フォント利用）なので、**配布状態で踏む**。

| DakutenType=2 + フォールバック有効（第4水準以上） | glyph タグ | 埋め込み TTF | 注記表示 |
|---|---:|---:|---:|
| 修正前 | 0 | 0 | 147 件 |
| 修正後 | 19 | 19 | 128 件 |
| （参考）フォールバック無効 | 19 | 19 | 0 件 |

原因は本書で決めた「1文字フォントがある文字は抑止しない」規則の穴。
`※［＃半濁点付き平仮名か、1-4-87］` は `か`(U+304B) ＋ 結合半濁点(U+309A) の **2 文字**に変換される。
結合半濁点は JIS に無いので水準は `LEVEL_OUT` になる一方、`hasGaijiFont` は
「1 文字」または「1 文字＋異体字セレクタ」しか見ないため、この 2 文字列を対象外にして `false` を返していた。
濁点フォントは `utf16FontMap` などのマップではなく、出力時に
`gaiji/dakuten/u<base>-u<mark>.ttf` をファイル名で直接引く**別経路**なので、マップ照会でも引っかからない。

修正（初版）: `isGaijiFallback` に `isDakutenKana` の判定を足し、仮名（と二の字点）＋濁点/半濁点の 2 文字は
水準に関わらず抑止しないようにした。
結合文字 (U+3099/U+309A) は `convertEscapedText` の前処理で U+309B/U+309C に正規化されるが、
`convertGaijiChuki` はその手前で動くので両方を受ける。

> **この初版の一律免除は誤りだった。**「`DakutenType` のどの設定でも端末フォント頼みにならない」は
> 基底字が第1・2水準のときしか成り立たず、`〻`・`ゕゖ`・`ㇰ–ㇿ` のように基底字自体が第3水準の場合や
> 合成結果が第3水準になる `ヷヸヹヺ`・`ゔ` には当てはまらない。
> `GaijiFallbackLevel=3` での退行につながった。下記「濁点付き文字は『対』で判断する」を参照。

> **教訓**: この機能で見つかった不具合 4 件はすべて「判定がフォント探索・出力地点を取りこぼす」同じ形。
> `convertTcyText` / `convertRubyText` / 濁点分岐は出力地点が多数あり `continue` で抜ける造りなので、
> ここに触るときは**出力地点を全部数えてから**判定の位置を決めること。
> ユニットテストだけでは見つからず、**配布物での dogfood が効いた**（同梱 ini の `DakutenType=2` が条件）。

**既知の制約**（Fable のフレッシュコンテキストレビューで確認・いずれも現状維持）

- **フォント免除は「必ず表示できる」ことまでは保証しない。**
  `convertTcyText` の非 IVS 経路は `printGlyphFontTag` で TTF の実在まで確かめてから水準判定に落ちるが、
  `convertReplacedChar` と 4バイト＋VS の分岐はマップ登録の有無（`hasGaijiFont`）だけで免除する。
  これらの経路はそもそも glyph span を出力しないため、免除された文字は素のまま端末フォント依存で出る。
  「フォントを登録した文字の従来出力を勝手に変えない」方を優先した結果で、意図的な非対称。
- **同じ長さのルビでは基底字だけが `〓` になり、後続のセレクタは残る。**
  `俠` ＋VS ＋`《きき》` のような入力で「`〓`＋セレクタ」になる。XML としては有効。
  上記「### 33.」のサロゲート分断と同じく、この分岐が `char` 単位であることに由来する。
- **`replace2Map`（2文字置換）より水準判定が先に効く。**
  置換対象の 1 文字目が抑止水準だと `〓` を出した直後に 2 文字目の置換が
  `setLength` でそれを巻き戻すため、`gaijiFallbackCount`（ログの件数）だけが過大になり得る。
  出力は置換結果が勝つので正しい。`convertTcyText` 側の既存経路も同じ順序。

### 濁点付き文字は「対」で判断する（2026-08-27・PR #87 追加修正）

PR #87 の初版は「仮名＋濁点/半濁点なら水準に関わらず抑止しない」という**一律の免除**だった。
この免除は `convertGaijiChuki`（注記経由）にしか無く、しかも実際の出力方法を見ていなかったため、
**`GaijiFallbackLevel=3` で退行**していた。

| `※［＃濁点付き二の字点］` | 出力 |
|---|---|
| PR #86 まで（level 3） | `〓（濁点付き二の字点）` |
| PR #87 初版（level 3） | `〓゛` ← **退行**（〓 と孤立した濁点） |
| PR #87 初版（level 4） | `<span class="glyph u303b-u3099">〻</span>` |

原因は 2 つ重なっている。

1. `convertTcyText` の**生文字フォールバックが濁点分岐より前**にある。
   `〻`(U+303B) や `ㇷ`(U+31F7) は**基底字自体が第3水準**なので `level=3` では
   `isRawCharFallback(ch[i])` で先に `〓` になり、`gaiji/dakuten/u303b-u3099.ttf` に
   到達せず後続の `゛` が孤立する。`か` のような第1・2水準の基底字では起きないため、
   第4水準以上で行った dogfood では発現しなかった。
2. 免除が `vertical` / `dakutenType` を見ていない。濁点分岐は `if (this.vertical)` 配下で、
   同梱 TTF を使うのは `dakutenType == 2` のときだけ。`dakutenType` 0/1 や横書きでは
   基底字がそのまま出るので、基底字が第3水準なら端末フォント頼みになる。

**修正方針: 仮名＋濁点/半濁点は 2 文字で 1 字とみなし、対で判断する。**
出せるなら丸ごと出す、出せないなら丸ごと `〓` にする。片方だけ落とさない。

判断は `isDakutenPairFallback(base, mark)` に集約した。

| 出力のされ方 | 水準判定の対象 |
|---|---|
| 合成済みの 1 文字になる（`が`・`ぱ`・`ヷ`・`ゔ` 等） | **合成後の文字** |
| 縦書き + `dakutenType=2` で `gaiji/dakuten/*.ttf` がある | 抑止しない（端末非依存） |
| それ以外（そのまま並べる / CSS で重ねる / 横書き） | **基底字**（`゛゜` は第1・2水準なので見なくてよい） |

あわせて次を直した。

- 結合濁点/半濁点 U+3099/U+309A を、異体字セレクタと同じく `JisLevelUtil.maxLevel` の
  判定対象から外した（`isCombiningDakuten`）。単体では字にならず、出力時に
  U+309B/U+309C（第1・2水準）へ正規化されるため。
  これで `chuki_utf.txt:7328` の `※［＃「井に濁点」］`（井 ＋ U+3099・非仮名なので対にならない）も
  巻き添えにならなくなった。
- `convertReplacedChar`（同じ長さのルビ経路）も対で判断する。落とすときは
  濁点側を `'\0'` にして一緒に消す（このクラスの既存の「除去済み」表現に合わせた）。
  あわせて、同じ長さのルビのループで**本文が `'\0'` の位置にはルビを振らない**ようにした。
  これが無いと `〻゛《ああ》` が `<ruby>〓<rt>あ</rt><rt>あ</rt></ruby>` になり、
  1 文字の `〓` に 2 つルビが付く（Codex のレビューで発見）。
  `'\0'` を本文に書き込む生きたコードは他に無いので、この分岐は本修正でしか通らない。
- 濁点分岐が結合文字 U+3099/U+309A も受けるようにした。目次経路
  （`Epub3Writer` からの `convertTcyText(String)`）は `convertEscapedText` の正規化を
  通らないため、章名に結合文字が残ると濁点分岐に入れなかった。
  なお本文経路では濁点は必ず `i+1 >= begin+1` の位置に来るので、
  正規化ループが `begin+1` 始まりであることは影響しない。

**検証（配布物 ZIP + `test_data/test_gaiji.txt`）**

| 設定 | dakuten glyph | 埋め込み TTF | `〓` | `〓`＋孤立濁点 | epubcheck |
|---|---:|---:|---:|---:|---|
| 無効（初期値） | 19 | 19 | 0 | 0 | エラー0・警告0 |
| 第3水準以上 + `DakutenType=2` | **19** | **19** | 241 | **0** | エラー0・警告0 |
| 第4水準以上 + `DakutenType=2` | **19** | **19** | 168 | **0** | エラー0・警告0 |
| 第3水準以上 + `DakutenType=1` | 0 | 0 | 243 | **0** | エラー0・警告0 |
| （参考）PR #87 初版・第3水準以上 | 0 | 0 | — | あり | — |

`DakutenType=1`（CSS で重ねる）では `半濁点付き平仮名か` は抑止されず
（基底字 `か` が第1・2水準）、`濁点付き二の字点` だけが `〓（濁点付き二の字点）` になる。
`DakutenType=2` ではどちらも同梱フォントで出る。意図どおり。

**既定（フォールバック無効）の出力は修正前後で byte-identical**
（`dcterms:modified` のタイムスタンプのみ差分）。
