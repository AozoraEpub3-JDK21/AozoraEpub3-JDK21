# Windows SmartScreen 警告への対応（調査記録）

`AozoraEpub3.exe` の起動時に「Windows によって PC が保護されました」が表示される件の調査記録と、
対策の判断。ユーザー向けの回避手順は README / `docs/usage.md`（ja/en）に記載済みで、本書は
**なぜその手順で足りるのか / なぜ署名を今やらないのか**を残すためのもの。

調査日: 2026-07-25

---

## 1. 原因の特定（実測）

Windows 11 26200 上で、手元にある exe の署名状態と Mark of the Web (MotW) を比較した。

| ファイル | 署名 | MotW | SmartScreen |
|---|---|---|---|
| `desktop-touch-mcp\bin\bridge-host.exe` ほか 2 本 | 未署名 | なし | 出ない |
| `AozoraEpub3-win-x64\AozoraEpub3.Gui.exe`（.NET ポート） | — | なし | 出ない |
| `AozoraEpub3-1.3.6-jdk21\AozoraEpub3.exe`（配布版） | 未署名 | **あり** (`ZoneId=3`) | **出る** |
| `AozoraEpub3-1.3.0-jdk21\AozoraEpub3.exe`（配布版） | 未署名 | なし | 出ない |

**比較対象はすべて未署名だった。**つまり「未署名だから出る」わけではなく、
**MotW が付いているかどうか**が分岐点。SmartScreen は MotW を持つファイルにしか反応しない。

配布版 1.3.6 の exe に付いていた属性:

```
[ZoneTransfer] / ZoneId=3 / ReferrerUrl=C:\Users\harus\Downloads\AozoraEpub3-1.3.6-jdk21.zip
```

同じ配布 ZIP でも 1.3.0 には MotW が付いておらず、1.3.6 には付いている。
1.3.0 を**どう入手・展開したかの記録は残っていない**ため断定はできないが、
機構としては次の差が存在することを §2 で検証済みで、これが最も自然な説明:

- **エクスプローラで展開** → ZIP の MotW が中身のファイルすべてに伝播する
- **7-Zip など（既定設定）** → 伝播しない

## 2. 回避手順の検証（実測）

「展開前に許可すれば伝播しない」ことを、MotW を付けた ZIP を `Shell.Application`（エクスプローラと同じ COM）で
展開して確認した。

| 手順 | 展開後の exe の MotW |
|---|---|
| MotW 付きのまま展開 | **あり** |
| `Unblock-File` してから展開 | **なし** |

したがってユーザー向けには「**展開前に**プロパティ →「許可する」」を案内するのが正しい。

「詳細情報 → 実行」でも起動でき、**その選択は記録されるので同じファイルで繰り返し聞かれることはない**
（当初「毎回クリックが必要」と書いたが誤りで、レビューで訂正した）。
展開前に許可する利点は次の 2 点:

1. 警告画面自体が出ない（初回体験が良い）
2. **同梱の jar や設定ファイルの MotW も消える**。「実行」を押しても exe 以外の MotW は残る

**限界**: この手順は SmartScreen 用。Windows 11 の **Smart App Control** は MotW に依存せず未署名アプリを
ブロックし得るため、SAC 有効環境では回避できない（§4 のコード署名が必要）。
ユーザー向けドキュメントにもこの但し書きを入れてある。

## 3. マニフェストでは解決しない

Launch4j にはカスタム application manifest の埋め込み機能がある（`manifest` オプション）。
しかしマニフェストで制御できるのは **UAC 昇格レベル (`requestedExecutionLevel`) / `supportedOS` / DPI awareness** だけで、
SmartScreen・Smart App Control・Mark of the Web のいずれにも影響しない。

**「マニフェストで SmartScreen 警告を消す」ことはできない。**
マニフェスト追加が有益なのは `dpiAware` 宣言（Swing の高 DPI 表示改善）くらいで、これは別課題。

## 4. コード署名の検討（今回は見送り）

全ユーザーに対して警告を根本的に消せるのはコード署名だけ。ただし今回は見送る。

| 選択肢 | 評価 |
|---|---|
| OV 証明書（年 $200〜400 程度） | 署名してもレピュテーション蓄積までは警告が残る。個人 OSS には費用対効果が低い |
| EV 証明書（年 $300〜700 + ハードウェアトークン） | 即時レピュテーション優遇は近年公式の保証がなく、個人には過剰 |
| **Azure Trusted Signing**（現 **Artifact Signing**） | **最有力候補**。ただし下記の未確認事項あり |
| Microsoft Store 登録（MSIX） | 個人登録料 + JRE 同梱パッケージ化の工数が過大 |
| exe をやめる | exe 導入の動機（Smart App Control 対策、v1.2.9 / `386cb6a`）が失われるので不可。※ §2 のとおり未署名 exe は SAC にブロックされ得るが、それは「署名すれば通る形にはなっている」ということで、`.jar` 直叩きより前進している。署名を入れた時点で完成する対策なので、exe を廃止すると振り出しに戻る |

**Artifact Signing の未確認事項**（2026-07-25 時点）:

- サービス名が **「Artifact Signing」に改称済み**であることは公式価格ページで確認した
- 価格ティアは Basic（5,000 署名/月）/ Premium（100,000 署名/月）の 2 種だが、
  **公式価格ページでは金額が `$-` と伏せられており、実額を確認できなかった**
  （「価格計算ツールにサインインするか営業に問い合わせを」との案内）。
  月 $9.99 という数字が流通しているが、**公式ページでは裏が取れていない**
- **日本居住の個人が本人確認（individual validation）を通せるか**は未確認
- Smart App Control が Artifact Signing 署名を無条件で許可するかの最新仕様も要再確認

**再検討の条件**: 実際に Azure アカウントで見積もりを取り、個人の本人確認が通ること。
署名を入れてもレピュテーション蓄積までは警告が残るため、本書の回避手順の案内は署名後も残す。
